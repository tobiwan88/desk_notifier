# Feed Sensirion's index a humidity-corrected log resistance

**The most defensible BSEC-free route is to run Sensirion's open BSD-3 Gas Index (VOC) algorithm unmodified, fed with a humidity-compensated, scaled ln(R_gas), at T = 10.8 s, and to label its output as a relative index, never as a concentration.** The algorithm is a published, readable pipeline (recursive mean/std, gated learning, logistic map to 1..500 with "typical" pinned to 100, adaptive low-pass) that takes its sampling interval as an init parameter and is documented as "tested for 1 s and 10 s" ([Sensirion C source](https://raw.githubusercontent.com/Sensirion/gas-index-algorithm/master/sensirion_gas_index_algorithm/sensirion_gas_index_algorithm.c), [header](https://raw.githubusercontent.com/Sensirion/gas-index-algorithm/master/sensirion_gas_index_algorithm/sensirion_gas_index_algorithm.h)). The weak links are all outside the algorithm. First, **no one has published a validation of it on BME68x data**: the researchers found no BME680/688 adaptation of it. Second, the **humidity slope is unknown**: community values span roughly 0.03 to 0.2 per g/m3, and the only open numbers come from one hobbyist's fits. Third, **no peer-reviewed study validates BSEC or any DIY index against PID, FID, GC-MS or NDIR**, so the "defensible" part rests on the algorithm's pedigree and honest labelling, not on measured accuracy. A simple ceiling-ratio index (compensated resistance divided by a slowly tracked clean-air baseline, as in the MIT-licensed thstielow and SE_BME680 projects) is the best cross-check and fallback, and it fixes the one thing the Sensirion index cannot do: show a room that stays polluted. The four labels should follow worst-channel-wins across VOC index (100/150/250 cut-offs), RH and, if ever added, CO2, with health wording reserved for CO2 where the German UBA gives a basis. Every numeric constant for the BME688 below is a starting value to be fitted from the device's own logs, and the report marks each as such.

## Sensirion's pipeline is readable, and 10.8 s is a parameter change

The reference implementation (header says 3.2.0; a third-party Rust crate says it is based on 3.2.2) processes one raw tick value per call in four stages ([C source](https://raw.githubusercontent.com/Sensirion/gas-index-algorithm/master/sensirion_gas_index_algorithm/sensirion_gas_index_algorithm.c)). The input is clamped to 20001..52767 ticks and offset by 20000. A recursive estimator tracks mean and standard deviation with time constants of **12 h** (`TAU_MEAN_HOURS`, `TAU_VARIANCE_HOURS`), a fast start-up phase (tau 20 s for 0.75 h for the mean, variance learning until 1.45 h), and **gating** that slows learning while the index exceeds 340 (510 at start-up), for at most 180 min for VOC. A linear "mox model" computes `index_raw = -(sraw - mean)/(std + 220) * 230` (the 220 is `SRAW_STD_BONUS_VOC`, 230 the gain). A logistic with `K = -0.0065`, `X0 = 213` and `L = 500` maps this to 0..500, which at the default offset of 100 reduces to `500/(1+exp(-0.0065*(r-213)))`, so zero deviation gives exactly 100. Finally an adaptive two-speed low-pass (tau 20 s fast, 500 s slow, alpha -0.2) smooths the output. Sensirion states the 100 point is a moving average of about 24 h, that "past events will be forgotten after about twice the learning time", and that the output "does not represent absolute concentrations" ([Info Note](https://sensirion.com/media/documents/02232963/6294E043/Info_Note_VOC_Index.pdf), [VOC Index for Experts](https://cdn.sparkfun.com/assets/e/9/3/f/e/GAS_AN_SGP40_VOC_Index_for_Experts_D1.pdf)).

All durations enter through the sampling interval, and the library ships `GasIndexAlgorithm_init_with_sampling_interval(params, type, T)`. The README says the interval "can be increased to 10s" and that it must match the real readout interval ([README](https://github.com/Sensirion/gas-index-algorithm)). The SGP40 datasheet, however, specifies 1 s for the index algorithm ([SGP40 datasheet](https://sensirion.com/file/datasheet_sgp40)), so 10.8 s is slightly outside the "tested for 1 s and 10 s" statement; this is a small extrapolation, not a verified configuration. Hand-derived consequences at T = 10.8 s (our algebra on the quoted code, not executed): the steady-state mean and variance coefficient is about 2.5e-4 per sample, the initial mean coefficient 0.351, low-pass A1 0.351 and A2 0.0211, and the first five calls (uptime up to 54 s) return 0 because of the 45 s blackout. The first processed sample sees mean = 0 and produces a transient, so the UI should ignore the first 2-3 minutes of output. If a gas sample is invalid, calling `process(params, 0, &idx)` keeps time advancing and holds the last value (derived from the source flow).

**Ohms to ticks.** SRAW_VOC is documented as proportional to ln(R) of the sensing layer, with typical sensitivity of **-870 ticks per doubling of ethanol** (5 to 10 ppm; min -710, max -1030) ([SGP40 datasheet](https://sensirion.com/file/datasheet_sgp40)). The absolute ticks-per-ln(R) factor is not published, and nobody has published a BME68x port, so the scale S below is a suggestion. The proposal is `sraw = round(30000 + S*(lnRc - ln(50000)))` with `lnRc = ln(R_gas) + k*(AH - AH_ref)`. Polarity needs no flip: resistance falls with VOC and so do ticks. The centre 30000 is arbitrary because the algorithm learns its offset; it only has to keep the signal inside the clamp window (at S = 2000 there is room for ln R from -5 to +11 around 50 kOhm). The scale does matter, because sensitivity is set by `r = 230*dTicks/(std+220)`: with std near 50, `r = 0.852*dTicks`. Hand-computed closed-form responses at S = 2000 are a 2 % resistance drop giving index about 119, 5 % about 153, 10 % about 222 and 20 % about 374; at S = 1250, 10 % gives about 171 and 40 % about 447. A starting S of **2000** (search range 1250-3000) assumes a BME688 power-law exponent near 0.6, which is unverified. The suggested tuning rule is to pick S so that a deliberate test (breath on the sensor, alcohol wipe, cooking) reaches 200-400 and an open window or night ventilation goes below 80, then freeze it.

**What not to touch.** The library is invariant to a constant additive offset in sraw but not to scale, and any change of centre, S, k, AH_ref or heater profile invalidates stored state (stored mean and std live in tick space). Keep the Sensirion files unmodified; the float build carries fix16 baggage (offset folding at |mean| >= 100, a 32767 uptime cap) that is harmless in float.

**Licensing.** The repository LICENSE is **BSD-3-Clause**, "Copyright (c) 2021, Sensirion AG", with source headers dated 2022 ([LICENSE](https://raw.githubusercontent.com/Sensirion/gas-index-algorithm/master/LICENSE)). The obligations are to keep the copyright notice in source copies, reproduce it in documentation that accompanies binaries, and not use Sensirion's name to endorse derived products. A hand port to a C++ class is a derivative work and needs the same attribution; this is not legal advice. BSD-3 carries no express patent grant, and whether Sensirion holds patents on the algorithm was not researched.

## Humidity, not temperature, is the compensation that matters, and its slope is unknown

Every credible source treats water vapour as a reducing gas that lowers MOX resistance ([Sensirion MOX info note](https://sensirion.com/en/media/documents/0083CDF4/6294DFEA/Info_Note_MOX_sensor.pdf)). The strongest evidence for using **absolute humidity (AH)** rather than RH comes from a different sensor: Eugster et al. found AH "performed marginally better than vapor pressure or mixing ratio" for a Figaro TGS 2600 over -41 to 27 C ([Eugster 2020](https://amt.copernicus.org/articles/13/2681/2020/amt-13-2681-2020.pdf)). For the BME68x, the one author who fitted it (thstielow, Pimoroni forum and repo) reports "parallel streaks of constant slope with varying offset" in ln R versus humidity, with the offset drifting over days, and says AH compensation is "much better" than RH ([repo README](https://github.com/thstielow/raspi-bme680-iaq), [forum](https://forums.pimoroni.com/t/bme680-observed-gas-ohms-readings/6608?page=2)). That gives the functional form `ln R_comp = ln R + k*AH`, i.e. `R_comp = R*exp(k*AH)`. It is log-linear, which is a modelling choice; whether it holds over 25-70 % RH at 15-30 C on a BME688 is unverified.

AH comes from the SHT40 using the Sensirion/Magnus form `AH = 216.7*(RH/100)*6.112*exp(17.62*T/(243.12+T))/(273.15+T)` in g/m3 ([Sensirion flow-conversion note](https://www.farnell.com/datasheets/3744141.pdf); one later Sensirion document prints 243.21, which looks like a typo). At 22 C and 50 % RH this is about 9.7 g/m3, and 1 % RH is about 0.19 g/m3 at 22 C (our Magnus calculation). The SHT40 is preferable to the BME688's own T/RH because the latter is biased upward by PCB heat and the gas heater: Bosch says the internal temperature is "typically above ambient" ([BME688 datasheet](https://cdn.sparkfun.com/assets/0/a/b/6/7/BME688_Datasheet.pdf)), and a forum user measured +0.7 C and -2 % RH on a 320 C/150 ms pulse ([forum post 5](https://forums.pimoroni.com/t/bme680-observed-gas-ohms-readings/6608/5)). One of our inferences is worth testing but is unverified: warming a parcel of air conserves AH almost exactly (22.0 C/45 % gives 8.71 g/m3, 22.7 C/43 % gives 8.67), so AH is robust to the skew, and the SHT40 is mainly valuable for cleaner regressors and true temperature display. No temperature term on ambient T is recommended at the start, because the heater sets the film temperature; add one only if residuals vs T are structured. **No pressure term**: the Bosch gas-resistance conversion has no pressure or humidity term, and no pressure sensitivity was found ([BME688 datasheet](https://cdn.sparkfun.com/assets/0/a/b/6/7/BME688_Datasheet.pdf)).

**The slope conflict.** The sources disagree by a factor of about seven, and the disagreement exists inside one author's work. The forum formula is `ln(R) + 0.04*RH` (per %RH; the post's text says "subtracted" but the formula uses +, and the log base is not stated); the same author's later repo code defaults to **`ph_slope = 0.03` per g/m3**, read directly from `bme680IAQ.py` ([source](https://raw.githubusercontent.com/thstielow/raspi-bme680-iaq/main/bme680IAQ.py)). SE_BME680 (MIT) uses 0.03 and the 2026 Tasmota IAQ merge uses `PH_SLOPE 0.03` ([SE_BME680](https://github.com/steveeidemiller/SE_BME680), [Tasmota PR #25175](https://github.com/arendst/Tasmota/pull/25175)). These share one origin, so the repetition is not independent corroboration. Converting 0.04/%RH at 22 C gives about 0.2 per g/m3, which is the number one research note carried into its pipeline; at that slope R would fall about 6x between 25 and 70 % RH, which we judge steeper than typical and probably contaminated by occupancy (humidity and VOC rise together). A second research note proposed 0.06 per g/m3 purely as a bracketing guess, explicitly "not a published value". The author states the slope "depends strongly on the heating profile and polling frequency", so a constant measured at 1 Hz does not transfer to 10.8 s. The practical conclusion is that the starting value only needs to be in the right order of magnitude and the on-device fit decides. The cost of a wrong k is concrete (our arithmetic at S = 2000): a 3 g/m3 humidity step (shower) with an uncompensated true slope of 0.06 is 0.18 in ln R, which the index maps to about 340 (a false "BAD").

**Fitting k from the device's own log** (suggested protocol, adapted from the thstielow method). Log every cycle R_gas, SHT40 T/RH, BME T/RH, `heat_stab` and `gas_valid`, with a fixed heater profile and period throughout. Collect at least 7 days after the burn-in, spanning at least 5 g/m3 of AH and including a weekend or absence. Drop the first 30 min after boot, unstable-heater samples, and periods with known VOC sources or fast falling R. Regress `ln R = a(day) - k*AH` with a per-day intercept (it absorbs drift), using a robust estimator (Huber or Theil-Sen) or per-AH-bin upper envelope, because VOC events only push R down. Check k > 0 with a confidence interval, check that the residual correlation with AH is under about 0.1, and check that the daily baseline noise drops against uncompensated R. Refit when heater profile, cadence or hardware changes and after about 3-6 months.

**Heater profile is a hidden parameter.** The BME688 datasheet gives 200-400 C targets, programmable 1-4032 ms durations, "approximately 20-30 ms" to reach temperature, and `heat_stab` as the stability flag. Bosch's modes include LP at 3 s (0.9 mA) and a 10.8 s scan cycle ([BME688 datasheet](https://cdn.sparkfun.com/assets/0/a/b/6/7/BME688_Datasheet.pdf)). Resistance falls with higher heater temperature and longer heating, and a forum user reported about 250 kOhm at 1 s polling versus about 70 kOhm at 30 s with 320 C/40 ms, a single anecdote ([forum](https://forums.pimoroni.com/t/bme680-observed-gas-ohms-readings/6608.json)). The research did not establish which heater profile this firmware uses, so fix (temperature, duration, period) at build time and treat any change as a new sensor.

## Validation evidence is thin, and what exists argues for relative, trend-only claims

Across the literature the researchers found **no peer-reviewed study that validates BSEC IAQ, bVOC or eCO2 against PID, FID, GC-MS, NDIR CO2 or formaldehyde analysers with R, R2 or RMSE**. The one direct benchmark of the sensor family is Zhu et al. (IEEE TIM 2024): a BME680 against thermal-desorption GC-MS for alpha-pinene in dry argon, with LODs of **20-39 ppb** against 0.61 ppb for GC-MS, usable linearity only above 40 ppb, and sensor-to-sensor response variation above 30 % reduced to about 5-7 % by a two-point calibration (abstract only, raw resistance, no BSEC) ([Manchester record](https://research.manchester.ac.uk/en/publications/1c73ce70-51be-407e-8a42-df63782e3af1)). A 2025 chamber study of eight BME688 units found raw baseline differences "larger than 100 %" in some conditions, a 60 % average raw difference falling to 13 % after normalising by baseline, humidity reducing NO2 and isobutylene response (isobutylene by about an order of magnitude) while enhancing CO response, and a conclusion that the sensor suits "presence and trends, not absolute concentrations" ([Panzardi et al., Sensors 25, 7102](https://pmc.ncbi.nlm.nih.gov/articles/PMC12694370/)). That result matters for design: humidity affects different gases differently, so no single ln R vs RH term is gas-neutral, and per-unit baseline tracking is essential.

The best accuracy numbers come from a different system. The German VOC4IAQ project ran a calibrated, temperature-cycled multi-sensor model (BME688 plus ZMOD4410/4510, ENS160 and SGP40) and reached summed-VOC RMSE of 64 ppb (nRMSE 7 %), with ethanol, limonene, toluene and CO acceptable and formaldehyde (53 %), acetaldehyde (70 %) and acetic acid (76 %) poor ([VOC4IAQ final report](https://cms.lmt.uni-saarland.de/sitemedia/pdfs/Projekte/VOC4IAQ_Schlussbericht_08-2023.pdf), grey literature, in German). In that year-long field data the model tracked ethanol (r = 89 %) and isopropanol (75 %), correlation with other VOC was under 30 %, and **in homes with cosmetics, cleaning and cooking there was no correlation between CO2 and the VOC model**, while in offices dominated by people the two agreed. This is a multi-sensor model with a 144 s temperature cycle, not a single-temperature BME688 and not BSEC, so it shows that the hardware family carries information, not that a 10.8 s single-profile index will reach that accuracy. Forum evidence points the same way: a user with a Trotec BQ16 reference saw the BME680 read 3-4x higher TVOC, and a Bosch moderator said the sensor tracks trends, not absolute values ([Bosch forum](https://community.bosch-sensortec.com/t5/MEMS-sensors-forum/Precision-of-BME680/td-p/15809)). BSEC's eCO2 and bVOC are described by Bosch-side replies as scaled versions of the VOC signal under a human-breath assumption ([Bosch forum](https://community.bosch-sensortec.com/t5/MEMS-sensors-forum/Explanation-on-static-IAQ-breath-VOC-and-CO2-equivalent/m-p/7413), seen via search snippet only), so a DIY index should not claim CO2. A 2024 BME688 paper reports that IAQ is "strongly influenced by relative humidity" (abstract only) ([Botticini et al.](https://api.crossref.org/works/10.3390%2FS24103170)).

Drift and warm-up have equally weak numbers. Bosch specifies BSEC-corrected IAQ drift of +/-1 to 4 % and says unit spread is corrected only after the BSEC calibration period ([BME688 datasheet](https://cdn.sparkfun.com/assets/0/a/b/6/7/BME688_Datasheet.pdf)); no raw-resistance drift rate for the BME68x was found. Burn-in guidance conflicts: 5 min stabilisation in ESPHome's BSEC docs, "at least 24 hours" for new boards in the BME AI-Studio manual ([manual](https://cdn.sparkfun.com/assets/1/c/b/8/c/bst-bme688-an001.pdf)), 48 h in the Adafruit guide, and thstielow's report that resistance kept rising "even after some hours" with 400-500 kOhm only after about a week. The firmware should therefore treat the first 24-48 h of a new board as "uncalibrated" and withhold the score for the first minutes after every boot.

## Open code gives structure to reuse, and the licences decide what you may copy

No mature, validated BSEC-free implementation exists. Everything descends from Pimoroni's 2017 "25 % humidity / 75 % gas versus a burn-in baseline" example and thstielow's compensated-ceiling variant. The table ranks what the researchers read from source for a C++ port into this MIT repository.

| Project | Licence | What to reuse | Main weakness |
|---|---|---|---|
| [Sensirion gas-index-algorithm](https://github.com/Sensirion/gas-index-algorithm) | BSD-3-Clause | The whole algorithm, vendored unmodified with notice | Never run on BME68x by anyone found; designed for SGP4x |
| [SE_BME680](https://github.com/steveeidemiller/SE_BME680) (2025) | MIT | Staged init/burn-in/normal, 100-entry highest-values ceiling, decay timer, spurious-value limits, accuracy levels | No persistence; `millis()`/`double`/`new`; unconditional time decay; 225 kOhm max tuned to author's profile |
| [thstielow/raspi-bme680-iaq](https://github.com/thstielow/raspi-bme680-iaq) (2023) | MIT | Cleanest statement of AH, `exp(slope*AH)`, ceiling, squared ratio; best README on quirks | No persistence; early spike inflates the ceiling; no events |
| [Pimoroni indoor-air-quality.py](https://raw.githubusercontent.com/pimoroni/bme680-python/main/examples/indoor-air-quality.py) | MIT | Origin of the score the repo's `Tracker` already uses | Fixed 5 min baseline; no gas humidity compensation |
| [jamieede123/airquality](https://jamieede.com/posts/bme680-air-quality-monitor-pi-zero-w/) (2026) | MIT | Hourly p90-of-24 h baseline, persisted; vapour-pressure-conserving RH correction | Pimoroni scoring; sort-based percentile not MCU-friendly; very new |
| [Tasmota PR #25175](https://github.com/arendst/Tasmota/pull/25175) (merged 2026-11-06) | GPL-3.0 | Ideas only: asymmetric EMA ceiling, persisted baseline with range check, Hill-function 0..500 map | Cannot copy code into MIT repo; no field history; per-sample alphas |
| herrmannj/airq-mqtt, juergs library | No licence stated | Nothing (treat as all rights reserved) | Max-only baseline never decays |
| G6EJD/BME680-Example | All rights reserved, personal use | Nothing | Fixed 10k-300k bounds; probable averaging bug |
| ESPHome `bme680` doc lambda | Not checked | Nothing | `ln R + 0.04*RH` gives about 10-14 regardless of air, so it never leaves its own "Excellent" band |

The elements worth taking are structural. These are log-domain humidity compensation, an asymmetric baseline (fast up, very slow down), staged warm-up with a confidence flag, and a persisted baseline with a range check. Tasmota's design, re-derived from its published description, is `comp = R_kOhm*exp(0.03*AH)`, baseline = mean over the first 2880 samples, `x = max(0, baseline/comp - 1)`, `u = (3x)^2`, `IAQ = 500*u/(1+u)`. The baseline rises with alpha 0.005 when `comp > baseline` and falls with alpha 0.00001 otherwise (PR text: about 7 min and 2.3 days at 2 s polling). Our arithmetic says this reaches IAQ 250 at R = 0.75 x baseline. Its alphas are per sample, so at 10.8 s they must be rescaled with `alpha = 1 - exp(-dt/tau)`: tau of about 400 s and about 2.3 days become roughly 0.027 and 5.4e-5 per sample (suggestion). Whether re-implementing a GPL design's published constants from the PR description is acceptable is a licence judgement for the repository owner; the safe course is to take only the idea and choose your own constants.

## Four labels from worst-channel-wins, honest wording, and a persistence policy that survives reboots

**Health scales cannot be mapped to a relative VOC index.** The old UBA five-level TVOC table (0.3/1/3/10/25 mg/m3, 2007) sits among UBA's withdrawn concepts, and the current committee says TVOC permits no health assessment and only recommends avoiding "conspicuously high" values above **950 ug/m3** (the 95th percentile of the GerES V survey, not a toxicological limit) ([UBA AIR page](https://www.umweltbundesamt.de/themen/gesundheit/kommissionen-arbeitsgruppen/ausschuss-fuer-innenraumrichtwerte-vormals-ad-hoc), [Seifert 1999](https://www.umweltbundesamt.de/system/files/medien/pdfs/TVOC.pdf)). WELL and RESET quote 500 ug/m3 TVOC as acceptable, both through secondary summaries ([RESET](https://reset.build/standard/air/process)). Neither Sensirion nor Bosch defines an index-to-ug/m3 mapping for field use; Sensirion says a MOX sensor "is not able to detect the absolute VOC concentration" ([Experts deck](https://cdn.sparkfun.com/assets/e/9/3/f/e/GAS_AN_SGP40_VOC_Index_for_Experts_D1.pdf)). Bosch's datasheet attaches health sentences (headache, neurotoxic) to IAQ bands and cites a UBA 25 mg/m3 figure, which does not suit an adaptive index and should not be copied into the UI. The only primary-sourced German health anchors that apply are for CO2: UBA's **< 1000 ppm unbedenklich, 1000-2000 ppm auffaellig, > 2000 ppm inakzeptabel** ([UBA Leitwerte PDF](https://www.umweltbundesamt.de/system/files/medien/4031/bilder/dateien/hygienische_leitwerte_0.pdf)). The device has no CO2 sensor, so these only apply if one is added. Humidity has no regulator-published band; 40-60 % is a vendor/practitioner convention and WHO gives no single RH cut-off for mould ([Atmotube](https://support.atmotube.com/en/articles/10450324-sensor-thresholds), [WHO dampness and mould](https://www.who.int/europe/publications/i/item/WHO-EURO-2009-4256-44019-62079)).

**Suggested label mapping** (our design choice, anchored to the cited scales, untested on BME688 data). The VOC column uses the Sensirion scale, where 100 is typical, 150 is Sensirion's own example action trigger and Atmotube treats at least 250 as "polluted". These cut-offs apply only to an index calibrated to the same log-style 100 = 24 h typical scale; they do not transfer from Bosch IAQ.

| Label | VOC index | RH (sustained) | CO2 (optional) |
|---|---|---|---|
| VERY GOOD | <= 100 | 40-60 % | < 800 ppm |
| GOOD | 101-150 | 35-40 or 60-65 % | 800-999 ppm |
| OKAY | 151-250 | 30-35 or 65-70 % | 1000-1499 ppm |
| BAD | > 250 | < 30 or > 70 % | >= 1500 ppm (UBA "inakzeptabel" starts at 2000) |

Show which channel set the level. Add hysteresis at each boundary (suggested about 10 index points, to be tuned) because an index pinned to 100 by construction would otherwise flicker at the VERY GOOD edge. Humidity alone should rarely produce BAD, since mould risk is about duration. During warm-up display "warming up" instead of a level. The disclaimer pattern from the research: call it a "VOC index" or "air freshness vs. the last day", state that it is relative to this room's recent history and cannot show a constant pollution level, avoid health words for VOC levels, and keep the footnote "VOC value is a relative index (100 = this room's typical air over the last day), not a concentration".

**Events, baseline and persistence.** No published detector exists for BME68x indoor events: the only documented items are a hobbyist's "(delta resistance)/minute > threshold" kitchen trigger with no number ([MySensors](https://forum.mysensors.org/post/93288)), Sensirion's gated estimator, and generic CUSUM/Page-Hinkley defaults ([Menelaus](https://menelaus.readthedocs.io/en/latest/menelaus.change_detection.html)). The following are therefore suggestions to be tuned. Run detectors in the ln domain on the humidity-corrected series: smooth asymmetrically (alpha(30 s) = 0.30 when falling, alpha(120 s) = 0.085 when rising, after a median of 3), take the slope over about 65 s, and declare an onset at below -0.10 per minute (about -10 %/min) or "very fast" at below -0.4 per minute (spray, perfume). Use pollution depth `p = b - xf` against baseline b with hysteresis (on at p > 0.15 and z > 4, off at p < 0.07), plus a one-sided CUSUM with kappa = 0.5 sigma and h = 5 sigma, clipped at zero. Ventilation detection should be a joint rule, because gas alone is ambiguous: within 3 min, AH moves at least 0.5 g/m3 toward the outdoor AH (from the existing weather task), and T moves at least 0.3 K toward outdoor when |T_in - T_out| > 3 K, and the gas series is not falling faster than -0.05 per minute. When indoor and outdoor are within 3 K and 1 g/m3, report "unknown"; an unsupervised window-state method from T/RH alone has the same stated limit ([arXiv 2406.16957](https://arxiv.org/abs/2406.16957)). A shower raises AH away from drier outdoor air, so the toward-outdoor test excludes it. Event shapes (cooking falling over 1-5 min and recovering over 10-30 min, perfume recovering in 3-10 min, people slowly over 20-60 min) are engineering expectations with no source and must be measured.

Baselining is where the Sensirion index is strong and weak. Strong: gated learning, a 12 h time constant and a fast 0-1.5 h start-up phase are documented. Weak: Sensirion states that for very long events the index "starts going back to average after about 3 h", i.e. the gate times out and a persistently polluted room becomes "typical" ([Experts deck](https://cdn.sparkfun.com/assets/e/9/3/f/e/GAS_AN_SGP40_VOC_Index_for_Experts_D1.pdf)). The suggested remedy is to run a slow ceiling-ratio index in parallel (asymmetric baseline as above) and raise a "persistent pollution" flag instead of adopting the polluted level when the two disagree for several hours. For persistence, Sensirion's header allows saving state only after at least 3 h of continuous operation and warns against restoring after more than 10 min of interruption ([header copy](https://ftp.riken.jp/NetBSD/NetBSD-current/src/sys/dev/i2c/sensirion_voc_algorithm.h)), whereas ESPHome's code restores a stale state anyway, arguing it "still beats a fresh 12-hour learning phase", and writes only when the state has drifted from the stored copy, with a key that changes when configuration changes ([ESPHome source](https://api-docs-dev.esphome.io/sgp4x_8cpp_source)). A suggested policy: store mean and std (and the ceiling baseline) in one versioned NVS blob with CRC and an SNTP timestamp; save at most hourly after 3 h of uptime and only if the state moved; invalidate on any change of heater profile, S, k or centre; on restore use age from the SNTP clock (under 10 min: full restore; 10 min to 12 h: restore with the startup blackout extended and events suppressed for about 10 min; 12 h to 7 d: restore but treat as low confidence; over 7 d or unknown time: discard). The age thresholds are guesses; no source says how stale a BME688 baseline can be before it misleads.

## Ranked recommendation, starting constants and an offline protocol

**Rank 1: Sensirion VOC index on humidity-corrected scaled ln R (primary display value).** Per gas sample (every 10.8 s), accept only samples with `gas_valid` and `heat_stab` set (standard Bosch API fields, not verified in the notes against this repo's vendored driver); otherwise call `process(params, 0, &idx)`.
1. `AH = 216.7*(RH/100)*6.112*exp(17.62*T/(243.12+T))/(273.15+T)` from the SHT40.
2. `lnRc = ln(R_gas) + k*(AH - 10)`, with starting **k = 0.03 per g/m3** (the only value in running open code, units g/m3; fit range 0-0.25 is a suggestion; replace by the on-device fit within the first week).
3. `sraw = round(30000 + S*(lnRc - ln(50000)))`, starting **S = 2000** (range 1250-3000).
4. `GasIndexAlgorithm_init_with_sampling_interval(&p, VOC, 10.8f)` with defaults (offset 100, learning 12 h/12 h, gating 180 min, std_initial 50, gain 230).
5. Hide output for about 3 min after boot, label learning for 45 min to 1.5 h, treat the first 24-48 h of a new board as uncalibrated.
6. After a day check `get_states` std: above about 200 ticks means the signal is dominated by drift or humidity rather than noise, and k needs refinement (suggested rule from the research).

**Rank 2: ceiling-ratio index re-implemented in `core/` (cross-check, persistent-pollution detector and fallback).** `comp = R*exp(k*AH)`, `x = max(0, B/comp - 1)`, a bounded score such as `u = (3x)^2`, `score = 500*u/(1+u)`. Update B with `alpha_up = 1 - exp(-dt/400 s)` (about 0.027) when `comp > B` and `alpha_down = 1 - exp(-dt/200000 s)` (about 5.4e-5) otherwise (suggested, rescaled from the Tasmota ratios), seed B from a burn-in of tens of minutes, store B in NVS with a range check, and gate with an SE-style accuracy flag based on the spread of the baseline history. Ranked second because it is simpler and never adopts pollution, but it is not validated either and its 0..500 scale is a design choice (re-anchor to Bosch's 25/250 only if comparability matters).

**Rank 3: keep the current Pimoroni-style `Tracker` and add AH compensation and persistence.** Lowest effort, but the fixed-shape 25/75 split and highest-seen baseline are the least defensible and the notes record the author's own caveat that the example is "pretty naive". **Not recommended:** BSEC (closed source, restricted redistribution), copying Tasmota code (GPL-3.0), and any unlicensed or all-rights-reserved code (herrmannj, juergs, G6EJD).

**Offline evaluation protocol (suggested; no published protocol exists).** Log at the native 10.8 s rate: epoch (SNTP), raw R_gas unfiltered, `gas_valid`/`heat_stab`, BME T/RH/P, SHT40 T/RH, outdoor T/RH, button presses, boot counter and a marker field. At about 20 B per row in compact binary, 160 KB/day, so stream over the HTTP API or serial rather than into the 1.8 MB `storage` partition. Add labels from a `POST /api/label?type=cook|window|clean|spray|people` endpoint (start/end, intensity 1-3) and a retrospective plot pass to fix times to +/-1 min. Include scripted events, each repeated at least 10 times at different hours: boil water 5/10 min, fry 5 min, cleaner spray 2 and 10 sprays at 1 and 3 m, one perfume spray, window open 2/5/15 min in winter and summer, two people for 1 h, shower with and without the door open. Record at least 2 weeks for first tuning and 4-8 weeks to validate seasonal humidity regimes and state restore, with at least one multi-day absence; recordings under a day cannot test baseline behaviour because the algorithm uses 24 h statistics. Replay the CSVs through the same `core/` C++ on the host (the existing doctest/ASan harness fits): score at event level with a true positive when an alarm starts within [-1 min, +5 min] of the labelled onset, report precision, recall, onset delay and false alarms per day separately for scripted events and quiet days, split by day (tune on about 60 %, validate on the rest), optimise F-beta with beta = 0.5 under a false-alarm budget (for example at most 2 per day), and inject synthetic drift (+/-0.2 ln over a week), warm-up transients, reboots and stale-state restores. Run the Rank 1 and Rank 2 indices side by side on every trace and choose the primary on the replay results.

## Conflicts between sources and unverified items

The **humidity slope** has four values for one concept: 0.03 per g/m3 (code, three projects), 0.04 per %RH (forum formula and ESPHome docs lambda, about 0.2 per g/m3 at 22 C by our conversion), 0.06 per g/m3 (one note's bracketing guess), and 0.2 per g/m3 (another note's carried-over conversion). The authors say it depends on heater profile and polling, so none transfers and an earlier note's statement that the README gives "no numeric default" is superseded by the code. **Bosch IAQ anchors** conflict: Bosch's datasheet and forum say IAQ about 25 is "typical good" and about 250 "typical polluted" with up to four days of history ([Bosch Community](https://community.bosch-sensortec.com/mems-sensors-forum-jrmujtaw/post/bme688-bsec2-iaq-calibration---how-does-it-work-XSkaXJpdT4OEL1S)), while ESPHome's BSEC2 docs use 50 and 200 with a default `operating_age` of 28 days ([ESPHome](https://esphome.io/components/sensor/bme68x_bsec2/)); this was not resolved, which is one reason to avoid copying Bosch's scale. **Sensirion licence:** the event-detection note called the library MIT; the LICENSE read in another note is BSD-3-Clause, which is what this report uses. **Sensirion parameter ranges** differ between the older NetBSD header (gating 1..720 min, learning 1..72 h, 1 s) and the master header (gating 0 or 1..3000, learning 1..1000 h); the master source is used here. **Burn-in** is 5 min (ESPHome), 24 h (Bosch manual), 48 h (Adafruit) or days (forum). **Restore after reboot:** Sensirion warns against stale restores while ESPHome argues for them. **RESET** versions conflict on PM2.5 (35 vs 25 ug/m3), irrelevant here, and CO2 comparisons mix delta and absolute figures (EN 16798-1 deltas of 550/800/1350 above outdoor vs 950/1200/1750 absolute).

Unverified, in rough order of importance: the BME688 ln R slope per g/m3 and whether the AH log-linear form holds on this part; the S scale and the BME688 power-law exponent; the firmware's heater profile and how it changes absolute resistance and k; whether Sensirion's algorithm behaves sensibly on BME68x ln R at 10.8 s (nobody published this); `heat_stab` and `gas_valid` handling against the vendored Bosch API; the BME688 noise per sample (Bosch specifies 1.5 % RMS, our tick-noise estimate of 10-40 is unverified); raw drift rate per week or month; event shapes and recovery times; BME688 selectivity for the user's actual sources (ethanol evidence is multi-sensor); whether Sensirion holds patents on the algorithm; the 2023 Sensirion compliance note's ethanol-to-TVOC conversion factors; UBA's 2025 guidance document and the primary text of the 2007 TVOC table; the SGP40 clean-air tick level (do not rely on "about 30000"); and the full text of Botticini 2024, Marinov 2021, Yurko 2019 and several Bosch forum posts (read through search snippets only).

## Conclusion

The research changes the question. A "real" BSEC replacement is not the hard part, because Sensirion publishes a battle-tested relative index and a 10.8 s cadence is a parameter. The hard parts are the two things only the device's own data can supply: the humidity slope for this heater profile and the scale S that makes a breath, a wipe and a window opening land at sensible index values. That makes the first week of logging the decisive engineering step, and it argues for shipping the index as honestly relative, with a parallel ceiling-ratio check that catches the failure Sensirion itself documents (a room that stays polluted becomes "typical" after about 3 h).

The second takeaway is about claims. The evidence says MOX sensors of this class track trends, respond well to alcohol-type events and poorly to formaldehyde, and vary 30-60 % unit to unit before normalisation, so a defensible UI says "fresher or staler than usual" and "ventilate", not "healthy" or "unhealthy". Health-style language belongs only to CO2 and, if ever added, to PM, where UBA and WHO give anchors.
